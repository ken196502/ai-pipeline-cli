# 机房 IP 限流下 Grok 优雅处理方案

## 1. 根因确认与真实网络分析
1. **为什么用户在手机/本地电脑上有额度，但在服务器上报限额？**
   - 经过真实测试与网络定位，服务器当前出口 IP（`104.238.221.29`）属于数据中心机房 IP。
   - X (Twitter) 针对机房 IP 下的免费 Grok 调用实施了极其严苛的指纹风控与频次限制：只要检测到自动化行为或机房出口，提问立即被服务器端直接拦截并返回 `More Grok with Premium. You have reached your Grok usage limit.`。
   - 用户在本地家庭/手机干净原生网络下仍能继续对话，但在服务器上被 X 彻底风控。

2. **核心业务架构重构（Grok 增强 vs 核心流程）**：
   - xdev 流水线的核心事实基础来自 **Stage 1 推文抓取** 与 **Stage 3 定向抓取的长文/外链文档（通常几千字技术原文）**。
   - Stage 4 的 Grok 联网仅作为可选的附加背景补充（Enrichment），绝不能因为一个第三方网页端机房风控，就让整个推文萃取与成稿流程直接瘫痪。
   - **严守 No-Fallback 原则**：若 Grok 遭遇限流，**绝不塞假数据伪装成功**；而是明确将 Stage 4 状态标记为 `skipped-due-to-ip-rate-limit`，成稿时仅使用真实推文与已爬取的长文外链，实事求是。

## 2. 改造方案
1. **Stage 4 容错降级（真实标记，不造假）**：
   - 在 `execute.ts` 中，调用 `driver.askGrok()` 时：
     - 若成功拿到有效学术调研，存盘并注入素材；
     - 若捕获到配额耗尽异常（`You have reached your Grok usage limit`），明确在日志与执行报告中记录警告，**跳过 Grok 素材注入，流水线继续前行**，绝不中断全流程，也绝不生成垃圾空文件。
2. **Phase 0 冒烟测试适应**：
   - 冒烟测试若检测到 Grok 限额，输出明确黄色告警并退出码 0 放行，避免阻断流水线。
